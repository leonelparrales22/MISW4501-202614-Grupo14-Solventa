# `stubs` — simuladores del ecosistema externo

El proyecto no integra proveedores reales (restricción de alcance). Cada subcarpeta es un módulo Go que simula un tercero, con latencia y fallos configurables para los experimentos (junto con Toxiproxy).

**Estado:** `openfinance` implementado (HA-D01; avisos de revocación, HU-M1.3-02); `opendata` y `kyc` implementados (HA-L01); `email` (HU-W1.3-03); `payment-gateway` (HA-D02); `policy-core` (HU-W2.1-01); el resto de carpetas sigue reservado.

| Stub | Simula |
|---|---|
| `openfinance` | Datos financieros consentidos (Open Finance): `GET /profiles/{id}` determinista por cliente y `GET /health`; `PORT` (9000) y `ARTIFICIAL_DELAY_MS` opcionales. **HU-M1.3-02:** `POST /consent-revocations` recibe el aviso de un consentimiento revocado con la cabecera `Idempotency-Key` obligatoria (400 sin ella): 201 la primera vez (`{revocation_reference, status: "confirmed", confirmed_at}`) y 200 con la misma clave y el mismo resultado. `REVOCATION_FAIL_FIRST` (los primeros N avisos responden 503) y `REVOCATION_UNRESPONSIVE_ENTITIES` (códigos de entidad, separados por comas, que siempre responden 503: revocación parcial) opcionales. `GET /debug/consent-revocations` separa los avisos recibidos de las revocaciones únicas por clave. **Cada aviso y cada consulta de perfil quedan en el log en una línea** (`consent revocation key=… entity=… consent=… new=…` y `profile request customer=…`): la evidencia en CloudWatch, donde `/debug` no se alcanza |
| `opendata` | Fuentes públicas (clima, geolocalización, listas oficiales): `GET /profiles/{id}` determinista (señal distinta a la de Open Finance) y `GET /health`; `PORT` (9010) y `ARTIFICIAL_DELAY_MS` opcionales |
| `kyc` | Verificación de identidad, listas restrictivas y AML: `GET /profiles/{id}` determinista (señal propia) y `GET /health`; `PORT` (9020) y `ARTIFICIAL_DELAY_MS` opcionales |
| `email` | Proveedor de correo: `POST /messages` (cabecera `Idempotency-Key` obligatoria; 201 si es nuevo, 200 si ya lo había aceptado) guarda el mensaje en memoria, `GET /messages?to=` lo lista para verificar lo que recibiría el asegurado y `GET /health`; `PORT` (9030), `ARTIFICIAL_DELAY_MS` y `FAIL_FIRST` (las primeras N peticiones responden 503) opcionales. **Cada mensaje nuevo queda además en el log en una sola línea** (`message accepted id=… to=… subject="…" idempotency_key=… body="…"`, con el enlace del documento), para leerlo donde `GET /messages` no se alcanza (CloudWatch Logs en AWS, HA-D02); un duplicado se registra sin el cuerpo. Se publica en ECR (`solventa/email`, `infra/terraform/bootstrap/cd-ecr`, HU-W1.3-02) y corre en la plataforma de T4 detrás de Cloud Map (`email.<entorno>.local:9030`) |
| `payment-gateway` | Cobro de primas y pago de indemnizaciones (HA-D02): `POST /charges` con la cabecera `Idempotency-Key` obligatoria registra y procesa el cobro **antes** de responder (si Toxiproxy corta la respuesta, el cobro ya ocurrió); la misma clave devuelve el mismo resultado sin cobrar otra vez (201 la primera vez, 200 después) y con otro monto responde 422 `idempotency_key_reused`; una referencia que contiene `declined` se rechaza con 402 `payment_declined` y `decline_code` 51. `GET /debug/charges` separa las solicitudes recibidas de los cobros reales por clave (la evidencia de 0 perdidos y 0 duplicados), `POST /debug/reset` y `GET /health`. `PORT` (9040; el 9030 es del stub `email`), `ARTIFICIAL_DELAY_MS` (después de registrar el cobro) y `SUPPORTS_IDEMPOTENCY=false` (simula un proveedor que no respeta la clave, para el contrafáctico) opcionales. Requisito para cualquier proveedor real: respetar la `Idempotency-Key` (decisión D-10). Igual que `email`, se publica en ECR (`solventa/payment-gateway`) y corre en la plataforma de T4 detrás de Cloud Map (`payment-gateway.<entorno>.local:9040`); su log (`charge request key=… reference=… status=… new_charge=…`) es la evidencia de los cobros reales en AWS. Desde T5, la tokenización de la tarjeta (`POST /tokens`, HU-W1.3-02) se publica **sin sesión ni API key** como `POST /pasarela/tokens` del API Gateway (5 req/s, ráfaga 10), en el mismo dominio del portal web: el stub queda además detrás del ALB, solo en `/tokens`; `/charges` y `/debug/*` no se exponen |
| `policy-core` | Core de pólizas (HU-W2.1-01): `GET /holders/{holder_id}/policies` y `GET /health`. **Determinista por titular** (hash del id, cualquier `sub` sirve sin sembrar): una póliza de Autos activa (`AU-<año>-<6 dígitos>`, con placa; no cubre `glass` cuando el hash es par), una de Hogar activa (`HG-…`, `water_damage`), una de Viaje activa (`VJ-…`, paramétrica) y una de Autos vencida hace 30 días; la vigencia se ancla al día UTC actual. `POLICY_SEED_FILE` (JSON `{"holders":{"<id>":[…]}}`) reemplaza las pólizas de titulares concretos; `PORT` (9060) y `ARTIFICIAL_DELAY_MS` opcionales |
| `esignature` | Firma electrónica y notificación legal |
| `iot` | Telemetría/IoT (clima, vuelos) para eventos paramétricos |
| `embedded-partner` | Un socio de distribución que consume las APIs |

Los servicios nunca importan un stub: lo invocan por HTTP a través de los adaptadores de `pkg/adapters`.

El `Makefile` no corre lint ni pruebas sobre `stubs/`; se ejecutan aparte, por ejemplo
`golangci-lint run ./stubs/opendata/... ./stubs/kyc/...` y `go test -cover ./stubs/opendata/... ./stubs/kyc/...`.
